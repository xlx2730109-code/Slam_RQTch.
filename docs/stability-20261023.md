目标：固定“Jetson 突然连不上”的现象、证据、已做措施与未解问题，供离线分析和下次连接使用。**根因尚未确定**，本文区分实测、推测与已撤回的结论。

## 现象

| 项 | 内容 |
| --- | --- |
| 开机寿命 | 21:18（46 分钟）、22:16（11 分钟）、22:36（2 分钟）、22:43（12 分钟）、23:02（约 2 分钟）、23:17（17 分钟），均以日志与电压记录同时中断结束；23:38 起连续运行，00:00 时已 21 分钟（超过此前除 21:18 外的所有开机） |

## 假设与判断

| 假设 | 支持 | 反对或未证实 | 状态 |
| --- | --- | --- | --- |
| H1 时钟被 NTP 突然拨正，SLAM 的时间差爆炸，位置飞到千万米 | 位置 1.7×10⁷ m；开机时钟回跳 | 未取得时钟跳变与发散的先后日志 | 未验证 |
| H2 SLAM 发散占满 CPU 与内存，使 SSH 无法响应 | 提交 `add0f7e` 的说明；22:01 内存 31 GiB | 事实 1：多次停机前并无资源耗尽 | 只解释部分掉线 |
| H3 手机热点与运营商 NAT 使链路只能走中继 | 延迟 160–780 ms，`MappingVariesByDestIP: true`，不能直连 | 解释不了日志与电压记录同时中断 | 解释链路慢，不解释停机 |
| H4 瞬时断电或硬件复位 | 停机瞬间无预兆；日志与电压同时停写；此前团队专门做过“断电取证”记录 | 无电压低点证据 | 未排除 |
| H5 xHCI 错误风暴把内核卡死 | 事实 4、6、9 | 无法证明停机时刻的内核状态 | 最可疑，未证实 |
| ~~H6 读取大量 systemd 日志导致停机~~ | 三次停机前恰有日志读取 | 之后一条日志都没读仍停机 | **已撤回** |

## 已撤回的错误结论

| 结论 | 原因 |
| --- | --- |
| 雷达经 USB 网卡接入，应改接板载网口 | `eth1` 驱动为 `nvethernet`，即板载以太网，雷达本来就在上面；USB 网卡是 `eth0`，无线缆 |
| 读日志导致停机 | 见 H6 |
| “内存或 CPU 耗尽” 是停机的直接原因 | 见事实 1 |

## 已在原机应用的措施

脚本与回滚见 `deploy/hardening/`。**这些是针对可疑原因的缓解，不是已证实的修复**，是否降低了停机频率尚无足够观察。

| 措施 | 针对 | 应用状态 |
| --- | --- | --- |
| `jiaoda-fastlivo` 限制内存 12G、CPU 400%，降低优先级，普通输出丢弃，`swappiness` 置 0 | H2 | 已应用 |
| `sshd`、`tailscaled` 不被内存不足处理选中，CPU 份额提高；远程会话 slice 限 CPU 300% | H2 | 已应用 |
| `jiaoda-memguard`：可用内存低于 8 GiB 重启 SLAM，低于 3 GiB 结束其进程 | H2 | 已应用 |
| `jiaoda-netguard`：本机断网或 Tailscale 失效时逐级自愈，默认不重启整机 | H3 | 已应用 |
| `jiaoda-usbpower`：关闭 USB 自动挂起，设备电源常开 | H5 | 已应用 |
| `kernel.printk = 1 4 1 7`：内核控制台级别降为 1，避免报错同步写入慢速串口 | H5 | 已应用 |
| 网页摄像头改为按需打开，格式 MJPG 640×480、10 fps；相机发布降为 5 Hz | 降低 USB 带宽 | 已应用 |
| 停用 tracker | 磁盘写入（效果见事实 7，未达预期） | 已应用 |
| 黑匣子 `jiaoda-blackbox`：每秒记录负载、读写、USB 中断、卡等磁盘的进程数、最后一条内核消息、占 CPU 前三的进程 | 取证 | 已应用 |
| 关闭 Wi-Fi 省电 | H3 | 配置已写，原本已关闭 |
